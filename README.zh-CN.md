# 实验台 · Experiment Manager

[English](README.md) · [简体中文](README.zh-CN.md)

在自己的多台电脑上运行 GPU 实验，在一个网页里提交、查看和收集结果。
每次实验的代码版本、运行环境、参数、日志、指标和检查点放在一起，便于以后查找和复现。

**当前版本：0.2.0-rc.1，预览版。** 主控端和算力端是两个独立程序。
主控端负责管理，算力端负责训练。同一台 Windows 电脑想“自己调度自己的显卡”，需要同时安装这两个版本。

## 应该下载哪一个？

到 [GitHub Releases](https://github.com/Pencilfinely/experiment-manager/releases) 下载下表中的应用 ZIP。
不要把 GitHub 自动附带的 `Source code` 源码压缩包当成安装包。下载后先完整解压，再运行入口。

| 文件名后缀 | 安装在哪 | 启动入口 | 需要提前准备什么 |
|---|---|---|---|
| `windows-controller-x64` | Windows 11 主控电脑 | 双击 `Start-Controller.cmd` | 浏览器即可；包内自带 Python，不需要 WSL 或 Docker |
| `windows-worker-x64` | Windows 11 NVIDIA 显卡电脑 | 双击 `Start-Worker.cmd` | WSL2、Ubuntu 22.04 或更新版、已开启 WSL 集成的 Docker Desktop、NVIDIA Windows 驱动 |
| `ubuntu-worker-x64` | 原生 Ubuntu 22.04 或更新版的 NVIDIA 显卡电脑/服务器 | 在解压目录运行 `bash Start-Worker.sh` | Docker Engine、NVIDIA Linux 驱动和 NVIDIA Container Toolkit；普通用户能运行 Docker |

三个包属于同一个 Release，使用相同版本号。当前面向 x86-64，不支持 ARM 或 AMD/Intel 显卡训练。
Ubuntu 包是算力端，不是主控与算力合并版。

算力端在 Ubuntu 中使用 Python 3.10+ 和 Git；缺少这两项时，启动器会通过 `apt` 安装，可能需要输入自己的 Linux `sudo` 密码。
启动器不会替换显卡驱动，也不会安装 WSL 或 Docker。首次准备环境建议至少留出 8 GiB 磁盘空间；数据集、源码和训练结果需要额外空间。

## 先理解这几个角色

```text
主控电脑                                  算力电脑
浏览器 → 主控端 ────── 局域网/可信私网 ────── 算力端 → Docker → 训练程序
           ↑                                  │
           └──────── 日志、指标、结果文件 ──────┘
```

**主控端**保存实验清单、安排任务、收集结果。**算力端**检查机器有哪些可用资源，准备输入，再启动训练容器。
**Docker**给实验提供固定的 Linux/Python 环境。因此，镜像里的 Ubuntu 版本与宿主机 Ubuntu 不同是正常的，软件不会因此替换宿主系统。

机器之间要先能通过局域网或可信私网（例如自己的 VPN）互通。“都在校园网里”本身不保证互通。
算力端主动连接主控端，算力端不需要额外开放入站端口。程序会列出可能的主控地址，但无法替用户打通被路由器、校园网或 VPN 策略阻断的网络。

## 第一次安装，按这四步做

### 第一步：启动主控端

1. 在 Windows 主控电脑上，将主控 ZIP 解压到准备长期保留的目录，例如 `C:\Apps\ExperimentManager-Controller`。
2. 双击 **`Start-Controller.cmd`**。程序自动创建自己的数据目录，并打开已完成本机登录的实验台网页。
3. 保持启动后出现的终端窗口运行。可以关掉浏览器，之后再打开；关闭主控终端会停止服务。

数据默认存放在 `%LOCALAPPDATA%\ExperimentManager\controller`，与解压出来的程序目录分开。
首次启动会在 8765～8784 中选择第一个可用端口并记住它，以后保持不变。再次双击会打开已经运行的同一个主控端，避免重复启动。

### 第二步：给每台算力机生成配对文件

1. 在主控网页中点击 **“添加算力机 / Add worker”**。
2. 给这台机器起一个独立名称，例如 `gpu-desktop`、`ubuntu-server`。使用英文字母、数字、下划线、点或短横线。
3. 选择或填写**算力机能够访问的主控地址**，要包含端口。例如主控电脑的局域网 IP 或私网 VPN IP。
   不要给远程机器填 `localhost`，它表示“运行这个请求的机器自己”。Windows 和 WSL 也有各自的网络环境，自己调度自己的 WSL 显卡时，同样应填写从 WSL 可达的 Windows 地址。
4. 点击 **“下载配对文件 / Download pairing file”**，得到 `名称.pairing.json`。把这个小文件传到对应算力机。

这个文件相当于这台算力机的工作证，不需要打开或编辑。
每台电脑使用不同的名称和文件。重装同一台算力机时可以重新导出原名称，身份保持不变；不要把同一个身份交给两台机器。
配对文件只包含算力端自己的凭证，不包含主控管理员凭证。

如果 Windows 防火墙阻止远程连接，在主控解压目录运行 **`Allow-Worker-Connections.cmd`**，输入那台算力机的 IPv4 地址，并同意 Windows 管理员授权。
它只放行“这个来源 IP → 当前主控 TCP 端口”。该工具不修改路由器或 VPN，校园网/私网本身的阻断仍需要在对应网络层解决。
Windows 中明确的“阻止”规则会优先于“允许”规则。如果之前拒绝过本主控程序的联网弹窗，请到 **Windows Defender 防火墙 → 高级设置 → 入站规则**，检查该安装目录下 `runtime\python.exe` 对应的规则。工具检测到这种阻止时会说明原因，保留规则供你确认。

### 第三步：启动算力端

**Windows 算力机：**

1. 启动 Docker Desktop，在 **Settings → Resources → WSL Integration** 中开启所用 Ubuntu 的集成。
2. 将 Windows 算力 ZIP 完整解压到本地目录，把这一台机器的 `名称.pairing.json` 放在 `Start-Worker.cmd` 旁边。
3. 双击 **`Start-Worker.cmd`**。如果有多个 WSL 发行版，首次选择要使用的那一个，程序会记住。

**原生 Ubuntu 算力机：**

1. 解压 Ubuntu 算力 ZIP，把配对文件放在 `Start-Worker.sh` 旁边。
2. 在解压目录打开终端，或通过 SSH 登录后 `cd` 进入该目录。
3. 用普通 Linux 用户运行 **`bash Start-Worker.sh`**，不要以 root 或 `sudo bash` 方式运行整个程序。

之后程序会自动完成：

1. 用配对文件连接主控，检查本机 Docker、NVIDIA 显卡和剩余磁盘空间。
2. 准备带版本记录的程序副本和一个用于验收的 Git 快照。
3. 从固定的 PyTorch/CUDA 基础镜像构建环境，在仅监听 `127.0.0.1:5001` 的本机镜像仓库中固定镜像摘要。
4. 在与真实任务相同的受限容器条件下，逐张检查显卡 UUID 并实际运行 CUDA 运算。
5. 生成节点配置、保守的资源预算和 GPU 验收任务模板，然后启动接单程序。

首次镜像下载较大，可能需要几分钟甚至更久。出错时窗口会说明原因和日志位置；修复后重新运行同一个入口，已完成的镜像准备可以复用。
平时再次启动会直接使用保存的配置，自动重连，也能处理主控暂时离线的情况。

算力端数据保存在 **Ubuntu 内部**的 `~/.local/share/experiment-manager/worker`。
首次配对和运行环境配置不需要手改 JSON。使用节点时保持 Docker 和算力端终端运行。

### 第四步：从网页提交一次验收任务

1. 等主控网页的“计算节点”中出现这台机器，并显示在线。
2. 点击它的 **“填入任务 / Use: GPU-check-…”**。
3. 检查右侧已填入的任务，点击一次 **“提交到队列”**。参数组合 `{}` 表示只运行一次。
4. 打开这个实验，等状态变成 **“已完成 / succeeded”**。
5. 下载 `result.json`，确认里面有 `"status": "passed"`。再确认节点的待回传文件数为 0。

这一步验证的是“网页提交 → 分配 → 真正的 GPU 容器执行 → 文件回传”的完整链路。
它不是科研实验，也不能用它的计算量或耗时推算模型训练性能。

## 如何换成自己的实验？

算力端安装解决的是管理软件自己的环境和配置。使用哪份算法、哪份数据、哪些科研参数，需要由项目本身决定；安装器不能自动猜出所有项目的依赖和正确设置。

如果已有兼容预置 PyTorch 环境的本机 Git 项目：

1. 先等已有工作完成或妥善停止，退出算力端终端，再双击 Windows 的 **`Configure-Project.cmd`**；Ubuntu 则运行 **`bash Configure-Project.sh`**。
2. 依次输入项目名、本机 Git 仓库根目录、训练命令，以及可选的数据目录。仓库需要是干净的已提交版本；向导不会替你提交或丢弃科研代码修改。
3. 重新启动算力端，主控网页的节点下就会出现这个项目的任务模板。
4. 填入模板后，在实验编辑器中设置训练参数和合适的 GPU/RAM/CPU 预算，再提交。自动生成的预算是起始值，不是实测值，也不保证任意模型都能放下。

源码以只读方式放在容器 `/workspace/code`；输出应写到 `/workspace/run`。
可选数据目录登记为 `项目名-data-v1`，只读挂载到 `/assets/项目名-data-v1`。
随软件提供的 SDK 可以读取这些路径和参数、上报指标、检查停止请求、发布检查点。如果原程序向源码目录直接写输出，需要先调整它的输出位置。

[运行与算法接入说明](docs/OPERATIONS.zh-CN.md)包含完整的小示例、SASRec 接入步骤、参数组合、并发条件、排错、备份和升级方法。
公开安装包不附带外部 SASRec 实现、私有算法仓库或科研数据集。

## 显卡现在能怎么分配？

| 运行方式 | 当前支持情况 |
|---|---|
| 一张卡跑一个实验 | 支持；自动配置默认让每个节点同时运行一个任务 |
| 多张卡各跑不同实验 | 支持，需要提高节点并发上限并满足资源预算 |
| 一张卡同时跑多个独立实验 | 支持，需要任务允许共享、单卡并发上限允许且预算足够 |
| 多张卡或多台机器合跑同一个实验 | 尚未实现，需要训练代码和调度器共同支持 |
| 自动判断哪种分配最快 | 尚未实现 |

程序给每个实验分配一个物理 GPU UUID，训练程序看到自己的逻辑 `cuda:0`。
这在 WSL 中尤其重要：仅靠 Docker 的选卡参数，有时仍会让 PyTorch 看到多张卡。进程选卡不等于硬件安全隔离。
空闲显存不等于空闲算力。默认配置先保证单任务运行清楚、可测；共享是否值得，应以实际完成时间为依据。
软件不会为了“优化利用率”偷偷修改 batch、精度或学习率。

## 日常使用与当前边界

- 主控离线后，算力端可以继续**已经分配且输入已缓存**的任务，重连后补传记录与文件。尚未准备好的任务可能仍需访问代码或镜像；主控离线时无法向它提交新任务。
- 可靠停止/恢复依赖算法保存完整训练状态。仅把普通程序装进 Docker，不会自动获得模型、优化器和随机状态的完整恢复；SASRec 适配器对此做了专门处理。
- 实验状态“已完成”时，文件可能仍在上传。关机前同时检查状态与待回传数量。
- 预览版使用前台启动入口，没有安装系统服务。Windows 睡眠、注销、重启或停止 Docker 都可能影响计算。目前没有签名 MSI、无人值守系统安装或自动升级。
- 仅在本机或可信私网使用主控端，不要直接暴露公网。它使用凭证认证，不是面向陌生用户的公共多租户服务。

## 开发与打包

管理程序使用 Python 标准库；源码运行需要 Python 3.10+。只有真正执行 SASRec/CUDA 的环境需要 PyTorch/NumPy。

```bash
python -m unittest discover -s tests -t . -v
python scripts/build_release.py --download-python
```

构建脚本只从明确的文件白名单打包，核对官方 Python 运行时的 SHA256，生成逐文件清单和 `SHA256SUMS.txt`。
运行数据、配对文件、个人部署记录、外部算法和数据集均不进入公开包。单元测试不等于显卡认证，目标硬件仍需实际验收。
