# 算法接入：到底要改什么？

[English](ALGORITHM-INTEGRATION.md) · [安装说明](../README.zh-CN.md)

先分清三件事：**适配算法通常只做一次，登记机器在每个目标节点做一次，提交实验则每天都可以做。** 不应当每换一个 seed 就重新装 Docker、构建环境或搬一遍项目。

## 你已经有可以正常训练的项目

实验台不会替换模型、损失函数、采样方法或优化器。它需要知道：

| 原来你手动决定 | 实验台运行时提供 | 训练程序需要怎样接收 |
|---|---|---|
| 本次学习率、seed、epoch 等 | 一个参数 JSON 文件 | 读 `EXPERIMENT_PARAMS`，或用 `Run().params` |
| 数据放在哪 | 只读的数据目录 | 从 `Run().assets` 取得登记的数据路径 |
| 输出保存在哪 | 本次实验独享的可写目录 | 写入 `Run().output`，不要写回源码目录 |
| 使用哪张物理显卡 | 节点已经选好的 GPU | 在容器里用 `cuda:0`，不固定物理卡号 |

**如果原程序已有命令行参数接受这些值，通常加一个外部启动包装即可。** 包装器读取实验台参数，再转换成原程序已有的命令行参数。不要改动训练数学过程。

如果原程序把数据路径、输出目录和超参数写死了，就需要把这些硬编码改成可传入的值。这个改动也能改善你平常在命令行中使用该程序的体验。

网页上的 `params.lr` 不会自动变成任意项目里的 `args.lr`：程序或包装器必须完成一次明确的映射。映射完成后，每次实验只在网页改参数即可。

## 先“能跑”，再考虑曲线和恢复

| 希望具备的能力 | 所需接入 |
|---|---|
| 启动训练、查看终端日志、拿到模型文件 | 训练命令能在容器中运行，正确读取输入，并把输出放进实验目录 |
| 网页实时显示 loss、Recall 等曲线 | 在算法产生指标时调用 `run.metric(epoch, loss=loss_value)`；终端里的任意一行文字不会自动变成曲线 |
| 正常完成时显示结构化结果 | 调用 `run.finish({...})` |
| 保存后停止、接着原状态继续 | 算法保存完整检查点，检查 `run.should_stop()`，并在恢复时还原模型、优化器、随机状态等 |

最后一项涉及训练的正确性，不能仅靠一个通用包装器自动完成。先接入前三项也是有效的接入；不要为了“支持恢复”误把从头重训当作继续训练。

SDK 的 `Run` 从 `expman.sdk` 导入。运行环境中已带有它。可直接照做的完整小项目见[运行说明中的 GPU 示例](OPERATIONS.zh-CN.md#一个从头能跑的小项目)。那个示例刻意没有宣称具备恢复功能。

## 对兼容的 SASRec_Original，无需再改训练代码

本项目已经提供 `expman.adapters.sasrec`，它负责把上述输入输出接到兼容的 SASRec_Original 上，并支持完整 epoch 的检查点恢复。

```text
你选择算法文件夹和科研配置
          ↓
导入工具保存当前源码快照、复制配置指定的数据、生成任务模板
          ↓
节点在自己的容器中启动现成的 SASRec 适配器
          ↓
适配器调用原来的训练代码，并把指标、检查点和结果交回实验台
```

这里的“兼容”有具体含义：该实现的 `src/experiment.py` 声明 schema 3 和 `external_sasrec_original_v1`，提供配置加载、训练入口和 epoch 回调。**不是任何叫 SASRec 的 GitHub 仓库都满足这个接口。** 导入工具先静态检查接口；实际可用性仍应通过短跑或 smoke 验证。

### 简化导入工具（当前源码版新增，尚不包含在 v0.2.0-rc.1 ZIP）

在已完成算力端配置的那台机器上，退出算力端终端。在 **Ubuntu 中的 experiment-manager 源码目录**执行：

```bash
python3 -m expman.sasrec_setup
```

只回答两项：

1. **算法目录**：选择 `SASRec_Original` 本身，也就是里面直接有 `src` 的那一层。WSL 中可粘贴 Windows 的 `E:\...\SASRec_Original` 路径。
2. **科研配置**：例如 `config/video_games_full.json`。它相对于刚才的算法目录；直接回车采用此默认值。

工具从科研配置的 `dataset` 和 `data_root` 找到 train、valid、test 三个文件。`data_root` 的相对位置以算法目录为起点，沿用这个 SASRec 实现本来的规则。

工具自动完成：

- 复制 `src` 下的 Python 文件到私有版本目录；不复制旧输出、模型或原仓库历史。
- 在复制出来的目录中记录 Git 提交；原项目不需要是 Git 仓库，也不要求你把其他未完成工作先提交。
- 按文件内容登记数据版本，并生成命令、数据 ID、镜像、节点标签等字段。
- 生成 `sasrec-video-games-short` 与 `sasrec-video-games-formal` 两个模板。正式模板保留配置的科研参数；短跑模板只把 `epochs` 改为 3、`star_test` 改为 -1。GPU 由节点选择，容器中的逻辑 GPU 编号固定为 0。

导入**不会提交训练**。启动算力端后，去主控网页该节点下面点击 `short` 模板，参数组合保持 `{}`，点“提交到队列”。确认训练、验证、测试和结果回传完成后，再使用 `formal` 模板。

资源预算默认为 CPU 2、RAM 8192 MiB、GPU 6000 MiB、单任务独占卡。这是兼容 SASRec 的保守起始配置，不是对任意模型尺寸的容量承诺，也不是显存预分配。节点预算不足时会等待；可在任务编辑器中按实测结果调整。

原项目后续修改后，退出代理、再次导入、重新启动代理即可。已有实验仍指向原来的源码和数据版本；新模板指向新快照。不要手改私有快照目录。

多环境节点可以用 `--profile 环境名称` 明确选择已经验证的环境。其他数据集可使用另一份科研配置和 `--name 独立项目名`，避免覆盖同名模板。

## 换到另一台机器，需要再做什么？

算法适配不需要重写，但目标节点也必须有那份代码、数据和可用的运行环境。当前导入器登记的是**执行导入的节点**，不是向所有节点自动分发项目。

因此，在主力机导入的模板会匹配主力机；在 2080 节点登记的模板会匹配 2080。复制一个模板后只改节点标签并不能保证它能在另一台机器运行，因为数据路径、源码白名单和本地镜像也必须匹配。

本地导入适合先把单节点跑通。跨节点统一分发代码、数据和环境属于部署层工作，不能通过修改模型代码解决；当前版本也没有自动多卡合训。
